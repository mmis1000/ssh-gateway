SSH Gateway GitHub

Host your own tunnel gateway.

SSH Gateway gives anyone you let in a public HTTPS address for a local web server or a folder, with a request inspector and a SOCKS5 tunnel. Their machine only needs ssh. This guide sets up the server side on one Linux machine behind nginx.

1Requirements

  • A Linux server with a public IP address. Clients connect to it, it never connects out to them.
  • Node.js 22.12 or newer and git.
  • nginx, or another reverse proxy that terminates TLS and passes WebSocket upgrades. The gateway itself speaks plain HTTP.
  • Two domains you control, one for the gateway and one for user content, see the next step.

2Domains and DNS

The gateway answers on two names. The setup host serves the setup script, the landing page and the inspector. The content domain gets one subdomain per user, like brave-otter-42-k3x9qz.ugc.example.net.

Put user content on a different registrable domain than the setup host (example.net next to example.com, not ugc.example.com). Pages your users share then can not read or set cookies of your main site.

NameTypePoints to
gateway.example.comA / AAAAyour server
ugc.example.netA / AAAAyour server
*.ugc.example.netA / AAAAyour server, the wildcard covers every user

The rest of this guide uses these names, replace them with yours.

3Install

Build the server and the inspector app. The inspector has its own package.json in app/.

git clone https://github.com/mmis1000/ssh-gateway.git /opt/ssh-gateway
cd /opt/ssh-gateway
npm ci
(cd app && npm ci)
npm run build

Run it as its own user, which owns the project directory, so the data it keeps stays private:

sudo useradd --system --home-dir /opt/ssh-gateway --shell /usr/sbin/nologin ssh-gateway
sudo chown -R ssh-gateway: /opt/ssh-gateway

4Configure

Start from the example and edit config.json in the project directory:

cp config-example.json config.json
config.json
{
    "setupProtocol": "https",
    "setupHost": "gateway.example.com",
    "setupPort": 443,
    "httpProtocol": "https",
    "httpHost": "ugc.example.net",
    "httpPort": 443,
    "httpListen": 11080,
    "sshHost": "gateway.example.com",
    "sshPort": 11020,
    "sshListen": 11020,
    "socksHost": "gateway.example.com",
    "socksPort": 11081,
    "socksListen": 11081,
    "userListenPortLow": 30020,
    "userListenPortHigh": 30099,
    "trustedProxy": "localhost",
    "saveDir": "save",
    "setupRequireAuth": true,
    "setupAccount": "admin",
    "setupPassword": "a long random password"
}

Each service has a public host and port, printed in links and scripts, and a listen port the gateway binds. They differ when something sits in between, like nginx for HTTP or port forwarding on a router.

FieldMeaning
setupProtocol setupHost setupPortPublic address of the setup host.
httpProtocol httpHost httpPortPublic address of the content domain. Users get <name>.httpHost.
httpListenPort of the gateway's HTTP server, for both hosts. nginx proxies to it, keep it closed to the internet.
sshHost sshPort / sshListenWhere client scripts connect, and the port the SSH server binds.
socksHost socksPort / socksListenThe SOCKS5 tunnel into folder mode clients, public and bound.
userListenPortLow userListenPortHighRange the folder mode sshd picks a random port from, on the client machine. Pick a range that is free there.
trustedProxyWho may set X-Forwarded-For. localhost trusts nginx on the same machine, so the inspector shows real visitor addresses.
saveDirUsers, their keys and the SSH host keys. Relative to the directory the gateway is started in.
setupRequireAuth setupAccount setupPasswordAsk for this account before handing out a new script. Leave it on unless anyone on the internet should get a tunnel.

5TLS certificate

One certificate covers the setup host, the content domain and its wildcard. Wildcard certificates need a DNS challenge, the gateway does not answer HTTP challenges on user subdomains. With Let's Encrypt, use the certbot plugin for your DNS provider, for example Cloudflare: 

sudo certbot certonly --dns-cloudflare \
    --dns-cloudflare-credentials /root/.secrets/cloudflare.ini \
    -d gateway.example.com -d ugc.example.net -d '*.ugc.example.net'

Other providers have their own plugins (certbot-dns-route53, certbot-dns-digitalocean, …), or use acme.sh. Renewal then runs on its own.

6nginx

nginx terminates TLS for both domains and passes everything to httpListen, keeping the Host header, which is how the gateway tells the setup host and every user apart. Upgrades must pass through for the inspector and for users' WebSockets, and buffering is off so requests and responses stream through the tunnel.

/etc/nginx/conf.d/ssh-gateway.conf
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    listen 80;
    listen [::]:80;
    server_name gateway.example.com ugc.example.net *.ugc.example.net;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    server_name gateway.example.com ugc.example.net *.ugc.example.net;

    ssl_certificate     /etc/letsencrypt/live/gateway.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/gateway.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:11080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;

        # stream bodies through the tunnel instead of holding them here
        proxy_buffering off;
        proxy_request_buffering off;
        client_max_body_size 0;
        # long polling and WebSockets stay open
        proxy_read_timeout 1h;
        proxy_send_timeout 1h;
    }
}

nginx before 1.25.1 does not know http2 on;, write listen 443 ssl http2; there instead. Check and reload with sudo nginx -t && sudo systemctl reload nginx.

7Firewall

SSH and SOCKS5 go straight to the gateway, not through nginx. The gateway binds every interface, so close the internal HTTP port.

80, 443nginx, open
11020sshPort, open, clients connect here
11081socksPort, open
11080httpListen, closed, only nginx uses it
with ufw, which denies everything else by default
sudo ufw allow 80,443/tcp
sudo ufw allow 11020/tcp
sudo ufw allow 11081/tcp

Some office and hotel networks block ports other than 80 and 443. Clients there can not reach sshPort.

8Run as a service

The gateway reads config.json from the project directory and resolves saveDir and the inspector app against the directory it is started in, so WorkingDirectory must be the project directory.

/etc/systemd/system/ssh-gateway.service
[Unit]
Description=SSH Gateway
After=network-online.target
Wants=network-online.target

[Service]
User=ssh-gateway
WorkingDirectory=/opt/ssh-gateway
ExecStart=/usr/bin/node index.js
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now ssh-gateway
journalctl -u ssh-gateway -f

On the first start it creates save/ and generates the SSH host keys, and the log ends with the curl command to set up a client.

9Try it

Open https://gateway.example.com/ in a browser for the landing page your users see. Then, on any machine with ssh:

curl -X POST -u 'admin:a long random password' https://gateway.example.com/setup > run.sh
chmod +x run.sh
./run.sh

Each /setup creates a new user with its own address and keys, so hand out one script per person or machine. The script prints its public address, the inspector link and the SOCKS5 tunnel; ./run.sh --help lists its options.

10Upgrade and back up

Back up save/. It holds every user and the host keys. Losing the host keys makes every client script refuse to connect, since scripts trust only the keys they were made with.

upgrade
cd /opt/ssh-gateway
sudo -u ssh-gateway git pull
sudo -u ssh-gateway npm ci
sudo -u ssh-gateway sh -c 'cd app && npm ci'
sudo -u ssh-gateway npm run build
sudo systemctl restart ssh-gateway

Data from older versions is migrated on start, the old files are kept in save.backup-v1-<time>/. To see what would happen first, run npm run migrate -- --dry-run. When a newer client script is available, old scripts print the command to update themselves the next time they connect.

What the gateway can reach. In folder mode the client runs an sshd as the user, which lets the gateway read any file that user can, not only the shared folder, and connect to local ports for the SOCKS5 tunnel. Whoever runs the gateway is trusted with that, so tell your users.
